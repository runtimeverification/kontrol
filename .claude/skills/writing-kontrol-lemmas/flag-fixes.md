# `kontrol prove` flag-level fixes and `.toml` configuration

Some stuck terms look like they need a custom lemma but are really
symptoms of a configuration the proof runner (or the Foundry profile)
just hasn't enabled. Before spending a session decomposing the stuck
expression, scan this file, `kontrol prove --help`, and the project's
`kontrol.toml` / `foundry.toml` for a configuration change that
targets the symptom directly. The lemma-test workflow still applies
once you're *writing* algebra — but flags and toml toggles are
cheaper, sounder, and invisible in the KCFG, so they're easy to miss.

## `--symbolic-immutables` — cures `EVMC_BAD_JUMP_DESTINATION` on contracts deployed with symbolic constructor args

**Symptom.** A proof that deploys a contract with `new Contract(x)`
where `x` is symbolic (directly, or transitively through a constructor
that assigns it to an `immutable`) halts with
`<statusCode> EVMC_BAD_JUMP_DESTINATION </statusCode>` — often on the
very first `JUMP` inside the constructor or the first deployed call.
The reliable tell is the shape of the `<program>` cell: a healthy
load shows a single concrete `Bytes` token, whereas a symbolic-
immutable deploy shows a `_+Bytes_` concatenation — typically
`concrete +Bytes #buf(WIDTH, _) +Bytes concrete`, with one `#buf`
slot per immutable (variable names and slot count vary by contract).
Whenever `<program>` is a `_+Bytes_` term, `<jumpDests>` will be
empty or missing the JUMPDESTs of the surrounding concrete bytecode,
and that's the signal to reach for the flag.

**Why it happens.** KEVM computes `<jumpDests>` from the bytecode when
it executes `#loadProgram BYTES`. The default rule only works when
`BYTES` is a single concrete `Bytes` token. A deployed contract with a
symbolic immutable ends up as
`concrete1 +Bytes #buf(32, X) +Bytes concrete2`, which the default
rule cannot scan. With no JUMPDESTs recorded, every subsequent
`JUMP DEST` falls through the guarded `[jump]` rule to the `owise`
case `JUMP _ => #end EVMC_BAD_JUMP_DESTINATION` in
`evm-semantics/evm.md`.

**Fix — add the flag, not a lemma.**

```bash
kontrol prove --match-test '<Contract>.<test>' --symbolic-immutables
```

`--symbolic-immutables` is an alias for `--break-on-load-program`. It
adds `EVM.program.load` to the cut-point rules, routing execution
through a custom Python step (`_exec_load_custom_step` in
`kevm_pyk/kevm.py`) that:

1. Flattens the bytecode along `_+Bytes_` into an alternating list of
   concrete `Bytes` tokens and symbolic `#buf(WIDTH, _)` slots.
2. Scans each concrete section for `0x5B` JUMPDEST opcodes while
   skipping PUSH1–PUSH32 immediates.
3. Fills each `#buf(WIDTH, _)` slot with `WIDTH` zero bytes — treating
   symbolic immutable storage as "definitely not a JUMPDEST", which
   matches solc's layout (immutable slots live in a data region no
   JUMPDEST ever points into).
4. Writes the resulting map into `<jumpDests>` and resumes execution.

**When to reach for it.**

- First `JUMP` / `JUMPI` in the proof halts `EVMC_BAD_JUMP_DESTINATION`.
- The stuck `<program>` cell contains a `#buf(...)` gap.
- The test deploys a contract that takes a symbolic constructor
  argument assigned to an `immutable`.

**When it's NOT the answer.** `EVMC_BAD_JUMP_DESTINATION` can also
arise from a genuinely wrong `JUMP` target — a symbolic `DEST`
computed from user input, or a mis-specified `initcode`. Those aren't
load-time symptoms; the bytecode is fully concrete and `<jumpDests>`
is populated, but the solver can't prove `DEST` lands on one. The
flag won't help there — you do need a lemma (or a stronger
precondition).

## `--run-constructor` / `run-constructor = true` — include constructor execution in test setup

**Two different defaults apply — check the project's toml before
assuming either.**

- **Kontrol's internal default** (no toml, CLI only): `run-constructor`
  is OFF. `kontrol prove --match-test ...` on its own will not run the
  constructor.
- **Default `kontrol.toml` generated by `kontrol init`**: sets
  `run-constructor = true` under `[prove.default]`. A fresh Kontrol
  project therefore *does* run the constructor unless someone removed
  or flipped that key.

Grep the project's `kontrol.toml` for `run-constructor` before
reasoning about whether the constructor actually ran. An absent key
falls back to Kontrol's internal default (OFF) — which is the
opposite of what the generated toml produces.

**Symptom (effective setting = OFF).** Storage reads during the test
return `0` (or default values) where the production contract would
have non-trivial constructor-initialised state. The proof branches on
a path condition that assumes default-initialised storage and gets
stuck — sometimes with an assertion failure that the real contract
could never trigger, sometimes with symbolic values the test was
expected to have already constrained.

**Why it happens.** When `run-constructor` is off, Kontrol starts each
test against deployed bytecode with *default* (zero) storage. The
contract's constructor — where e.g. `immutable` assignments,
`owner = msg.sender`, role grants, or initial parameter values get
written — is skipped. If the test assumes any of that initialisation
has already happened, the proof runs into stuck reads or spurious
revert paths.

**Fix — make sure the toml has it set (or pass the flag):**

```toml
[prove.default]
run-constructor = true
```

Or on the CLI:

```bash
kontrol prove --match-test '<Contract>.<test>' --run-constructor
```

If the toml already has `run-constructor = true` and symptoms persist,
check for a `--no-run-constructor` override on the CLI or a conflicting
`[prove.<profile>]` section shadowing `[prove.default]`.

**When to reach for it.**

- The contract under test has a non-trivial constructor that sets
  state the test relies on.
- Symptom is a storage read returning `0` or a revert on an
  uninitialised mapping lookup, not an algebraic stuck term.
- The test passes in `forge test` (which always runs the constructor)
  but fails in `kontrol prove`.

**When it's NOT the answer.** If the constructor itself is what's
stuck (e.g. `EVMC_BAD_JUMP_DESTINATION` inside the constructor on a
symbolic immutable), you need `--symbolic-immutables` above instead —
or in addition. `--run-constructor` enables constructor execution;
`--symbolic-immutables` changes how `<jumpDests>` is populated during
bytecode load.

## FFI in the Foundry profile — lets tests compute concrete fixtures

**Symptom.** `kontrol build` or the `setUp()` phase of a proof fails
with an FFI-related error (`vm.ffi` call rejected, or a helper library
like a signature generator reverts). Sometimes the symptom is one step
removed: a test that invokes a helper contract in `setUp()` to build
a PoP signature, an RLP-encoded blob, or a keccak preimage ends up
reading back zeros because the FFI call that was supposed to produce
the data silently didn't run.

**Why it happens.** Foundry's `vm.ffi(cmd)` cheatcode calls out to a
local executable during test setup to compute concrete fixture data.
Kontrol respects the same `ffi = true` / `ffi = false` switch from
`foundry.toml`. If FFI is disabled, `vm.ffi` calls return empty (or
revert, depending on version), and any downstream test state derived
from them is bogus.

**Fix — enable in the Foundry profile:**

```toml
# foundry.toml
[profile.default]
ffi = true

# Additionally, if the FFI script reads/writes local files:
fs_permissions = [
    { access = "read", path = "./test/data" },
]
```

Kontrol uses the `default` profile (or the profile under
`FOUNDRY_PROFILE`) for its compilation and test-setup execution, so
flipping this here is sufficient — there is no `kontrol prove --ffi`
CLI switch.

**When to reach for it.**

- The project's tests use `vm.ffi` to shell out to a script that
  builds a signature / ABI-encoded blob / hash preimage that's
  impractical to produce symbolically.
- `kontrol build` produces an FFI error, or the `setUp()` phase of a
  proof silently leaves helper-computed state empty.

**Important.** Kontrol pins FFI invocations at concrete values
captured during build. Do not rely on FFI to produce different values
across proof branches — the call resolves once per build.

## Configuration in `kontrol.toml` — beyond the CLI

`kontrol.toml` centralises proof-runner settings. Beyond
`run-constructor`, options that commonly unblock a stuck proof:

| Key (under `[prove.default]`) | Effect |
|---|---|
| `chainid = <N>` | Pins `block.chainid`. Kontrol defaults to 1 (mainnet) while Foundry defaults to 31337; a test that builds signed messages against `block.chainid` must agree with the signer's assumption. |
| `max-depth = <N>` | Raises the KCFG depth cap. Three defaults in play: Kontrol's internal default is `1000`, `--optimize-performance` bumps it to `100000`, and the `kontrol.toml` generated by `kontrol init` writes `25000`. Grep the project's toml before assuming a cap. |
| `max-iterations = <N>` | Caps booster iterations per node. Raise if legitimate reductions are being truncated. |
| `workers = <N>` | Parallelism. Does not affect correctness, only wall-clock. |
| `auxiliary-lemmas = true` | Enables Kontrol's bundled helper lemmas (they cover common patterns upstream; check what's already in scope before writing a duplicate). |
| `match-test = [ ... ]` | Scopes the run to listed tests. Faster iteration when hunting a single stuck proof. |

And under `[build.default]`:

| Key | Effect |
|---|---|
| `require = './test/kontrol/lemmas.k'` | Where the production lemma file lives. The scaffolding file (`run-lemma.k`) must NOT appear here. |
| `module-import = 'TestBase:KONTROL-LEMMAS'` | Pulls the lemma module into the K test base. Verify this matches the module name declared in `lemmas.k`. |

## Other `kontrol prove` flags worth knowing before writing a lemma

| Flag                      | Use when…                                                       |
| ------------------------- | --------------------------------------------------------------- |
| `--symbolic-immutables`   | As above — symbolic immutables / deploy-time symbolic bytecode. |
| `--run-constructor`       | As above — test assumes constructor-initialised storage. Off by Kontrol's internal default, but ON in the `kontrol.toml` generated by `kontrol init`; grep the toml. |
| `--enum-constraints`      | Stuck branches where an enum-typed arg isn't bounded to valid variants. |
| `--no-stack-checks`       | Pure performance — skips EVM stack under/overflow checks. |
| `--break-on-calls`        | KCFG is too coarse around external calls to diagnose where execution diverged. |
| `--break-on-jumpi`, `--break-on-jump` | Pin KCFG nodes at control-flow joins; helpful when a branch diverges unexpectedly. |
| `--break-on-storage`      | Pin KCFG nodes at SSTORE/SLOAD — useful when storage layout is the source of confusion. |
| `--break-on-cheatcodes`   | Pin KCFG nodes at cheatcode boundaries — useful when `vm.mockCall` / `vm.prank` is the suspected divergence. |
| `--break-every-step`      | Step-by-step debugging — very slow, use on minimal repro. |
| `--max-depth N`           | Cap KCFG depth. Kontrol's internal default is `1000`; `--optimize-performance` bumps it to `100000`; the `kontrol.toml` generated by `kontrol init` writes `25000`. Grep the toml. |
| `--no-fail-fast`          | `--fail-fast` is on by default, so a single failing branch cuts off work on siblings — pass `--no-fail-fast` (or set `fail-fast = false` in `kontrol.toml`) to drive every branch to completion and see all failures at once. |
| `--use-gas`               | Include gas semantics in the proof. Off by default (gas reasoning is expensive). |

Skim `kontrol prove --help` once per proof before committing to a
lemma — these flags are cheap to toggle and often subsume otherwise-
plausible algebraic fixes.
